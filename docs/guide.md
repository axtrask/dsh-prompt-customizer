## Как переходят фазы сессии

Фазы — это не жёсткая последовательность из трёх тактов: они выводятся из **durable-событий сессии**. Первый durable `tool/call` или `assistant/message` переводит сессию в следующую фазу, а одно `compaction/end` этот переход сбрасывает. Три части панели, посвящённые фазам, как раз и соответствуют этим трём состояниям.

Полная картина переходов (из фазы ввода можно попасть в фазу управляемого сжатия и минуя постоянную):

| Текущая фаза             | Событие                                          | Куда                        |
| ------------------------ | ------------------------------------------------ | --------------------------- |
| Фаза ввода               | первый durable `tool/call` / `assistant/message` | **Постоянная фаза**         |
| Фаза ввода               | `compaction/end`                                 | **Фаза управляемого сжатия** |
| Постоянная фаза          | `compaction/end` (сброс перехода)                | **Фаза управляемого сжатия** |
| Фаза управляемого сжатия | новый durable-сигнал после сжатия                | **Постоянная фаза**         |
| Любая                    | сессия субагента (`delegationDepth > 0`)         | всегда **постоянная фаза**  |
| Любая                    | чтение без сессии (список, предпросмотр)         | всегда **постоянная фаза**  |

Что именно разрешается на каждой фазе — три части панели один в один соответствуют полям конфига:

| Часть панели                                | Действующие блокировки секций | `phase` добавляемых секций | Действующий чёрный список инструментов                                   |
| ------------------------------------------- | -------------------------- | -------------------------- | ------------------------------------------------------------------------ |
| Промпт фазы ввода / инструменты фазы ввода | `sectionsBootstrap`      | `bootstrap` (+ `always`)   | `tools.bootstrap.exclude`, если не настроен — откат к статике            |
| Промпт постоянной фазы / инструменты постоянной фазы | `sections`               | `active` (+ `always`)      | `tools.exclude` (статика)                                                |
| Промпт фазы управляемого сжатия / инструменты | `sectionsCompaction`       | `compaction` (+ `always`)  | `tools.compaction.exclude`, если не настроен — откат к фазе ввода, затем к статике |

Два места, где легко споткнуться:

- **Добавляемые секции `always` присутствуют во всех трёх фазах**, и у каждой фазы своё пространство сортировки — поэтому записи фаз, которые создаёт плагин, стоят после группы `always` (в рантайме более поздняя запись в массиве перекрывает более раннюю, так что порядок фазы перевешивает глобальный порядок).
- **Вид фазы отвечает на вопрос «что разрешится в этом состоянии», а не «что когда-то было в сессии»**. Родные правила фаз пресета (zero-tool bootstrap, warmup и т. п.) действуют в тот же момент и могут изменить результат уже после других плагинов — см. [известные ограничения](#известные-ограничения).

## Интерфейс

Нажмите **Возможности** на боковой панели — откроется панель с тремя вкладками верхнего уровня: **Скиллы** (управление наборами скиллов), **MCP** (подключение Server и включение/выключение инструментов) и **Промпты** (всё остальное в этом разделе). Строки `/` для скиллов и вызова скиллов в сессии даёт ядро DSH — `@deepseek-ai/dsh-client-ui-skill`; плагин их не регистрирует повторно (пространство имён `skill`, одноимённые ключи слотов и одноимённый источник слэш-команд — все три принадлежат ядру, а повторная регистрация заставит `apply` плагина ядра выбросить исключение).

Два скриншота ниже — **вкладка «Промпты»** (сняты до 0.6.0: строка пресетов сверху была тогда чисто текстовыми табами, функциональность та же; скриншоты вкладок «Скиллы» / «MCP» пока не сделаны).

Дальше — детали **вкладки «Промпты»**: нажмите **Возможности → Промпты** на боковой панели, откроется отдельная панель. **Первая строка — чипы пресетов агента** (с 0.9.0 «Все агенты» больше нет), у каждого свой значок, имя и число кастомизаций этого пресета (оранжевая цифра = этот пресет правили отдельно); клик переключает цель редактирования, а при входе в панель выбирается первый доступный пресет. **Вторая строка — шапка кастомизации**: переключатель режимов (Промпты / Инструменты / Пресеты) + табы фаз (Фаза ввода / Постоянная фаза / Фаза управляемого сжатия, левая и правая колонки переключаются вместе) + синхронизация фаз и переключатель китайских промптов + Сохранить / Обновить / Закрыть.

**Режим «Промпты»**: слева список текущей фазы с чекбоксами (блокировка / замена / добавление / сортировка, внизу фильтр Все / Включены / Отключены), справа — живой предпросмотр итогового системного промпта после сборки:

## Возможности

### Управление наборами скиллов (вкладка «Скиллы»)

- **Бандлы скиллов**: разрозненные скиллы собираются в группы (реестр `.bundles.json` хранит и каноническое имя, и имя каталога — попадание находится, даже если имена каталогов расходятся); у бандла могут быть категории (не больше 8, каждая ≤24 символов), переименование синхронизирует `name` во frontmatter `SKILL.md`, удаление идёт по каноническому имени, а «повисшие» участники честно отображаются в отчёте.
- **Импорт**: перетащите или выберите ZIP либо папку — верхняя папка снимается автоматически, всё раскладывается в `<корень скиллов>/<имя>/SKILL.md` и сразу попадает в целевой бандл; при совпадении имени выдаётся понятная ошибка, а имена с разделителями пути отклоняются все без исключения (за пределы корня скиллов чтения нет).
- **Переключатели (два уровня: глобальный / пресета)**: включать и выключать можно и отдельный скилл, и целый бандл; уровень пресета ведёт собственный реестр (записи по каноническому имени) и действует только на этот пресет агента — с «глобальным» уровнем они друг друга не перекрывают.
- **Диагностика скиллов**: `/api/skill-health` показывает читаемость корней скиллов и согласованность их состава.
- **Откуда берутся скиллы (с 0.11.0 читается ядро)**: список в панели — это напрямую результат `ctx.skills.list({ cwd })`: все корни файловой системы (`<воркспейс>/.dsh/skills`, `<воркспейс>/.agents/skills`, `~/.dsh/skills`, `~/.agents/skills`, воркспейс определяется как «ближайший предок, содержащий `.git`») + `bundled` (поставляется с установкой) + `runtime` (пакет office) + провайдеры, которые регистрирует сам плагин. Порядок, дедупликация и приоритеты полностью определяются ядром по цепочке скоупов и cwd; плагин больше не сканирует сам и не берёт «объединение всех сессий».
- **Разделение труда с ядром**: источник скиллов `/` и строки вызова скиллов в сессии — забота ядра DSH `@deepseek-ai/dsh-client-ui-skill`, этот плагин их не регистрирует повторно (повторная регистрация заставит `apply` ядра выбросить исключение и утащит за собой всю цепочку загрузки клиентских плагинов); плагин даёт управленческую часть панели «Возможности» (импорт / группировка / переключатели / диагностика) и хостовые маршруты под ней.

### Подключение MCP Server (вкладка MCP)

- **Подключение в один шаг**: вставьте JSON / нативный для DSH YAML (форма `mcpServers`) / фрагмент строки `mcp-client` — панель сначала покажет предпросмотр того, что будет записано, а затем запишет в композицию пресета или в patch профиля — **с бэкапом перед записью**, одноимённые server пропускаются, невалидный serverName / небулево `enabled` отклоняются сразу.
- **Строки Server, привязанные к пресету**: прямо в панели можно добавить / удалить строку Server, принадлежащую конкретному пресету агента (запись идёт в `config.plugins` строки объявления этого пресета и через `configEditor` DSH попадает в patch профиля).
- **Послойное перекрытие**: два реестра — глобальные строки плюс уровень пресета (в уровне пресета две стороны: «наследует глобальное» и «своё», у каждой свой учёт); одноимённый Server, пришедший от пресета, приоритетнее унаследованной записи; глобальное выключение = вето, уровень пресета не может включить обратно (вернётся 409 с пояснением).
- **Включение/выключение на уровне инструментов**: инструменты относятся к своему Server по самому длинному совпадению (`my` и `my_server` образуют отдельные группы); можно выключить весь Server целиком или только несколько его инструментов; фильтрация при сборке, маршруты состояния и нативный каталог — из одного источника.
- **Рекомендованный список**: `/api/mcp-recommended` даёт шаблоны конфигов распространённых MCP Server — берите и подключайте.
- **У MCP Server есть только один источник — композиционная строка Cordis.** У ядра нет соглашения «читать `mcp.json` из какой-то папки» (поиск `mcps` по всему репозиторию не даёт ни одного совпадения), поэтому четырёхуровневый слой `mcps/`, который когда-то добавили в 0.10.x, в **0.11.0 удалён** — список, переключатели, добавление и удаление в панели действуют на композиционные строки (строку `mcp-client` / patch профиля), плагин больше не читает каталоги и не монтирует строки вместо кого-то.

### Секции промпта

- **Блокировка**: секция удаляется из результата сборки по имени + источнику. Заблокированная строка не исчезает — её по-прежнему можно редактировать и восстановить; блокировка значит лишь «не отдавать её модели».
- **Замена**: отредактируйте текст секции; поле предзаполняется текущим действующим текстом (для динамических секций панель пытается по мере сил разобрать реальное содержимое и показать его).
- **Добавление**: на каждой фазе кнопка «Добавить секцию» раскрывает форму — по имени + тексту создаётся новая секция с бейджем `Вручную`, её можно удалить в любой момент.
- **Сортировка**: тяните за ручку в начале строки или сдвигайте стрелками ↑/↓ по одной позиции. Порядок хранится как непрерывные виртуальные индексы с нуля — дубликатов и дробных order не бывает, и вписывать числа руками не нужно. **Пока сортировка не задана вручную, работает канонический `order` хоста** (тот же порядок, что получает модель: например, `tool:apply_patch` идёт после `tool:edit`); новые секции встают на позицию по order, а не приклеиваются в конец.
- **Перетаскивание**: перетащите строку из пула «Все секции системы» в список — это добавит её в текущую фазу (с исходным текстом из пула); перетащите строку обратно в пул — это удалит её из текущей фазы (добавленную — отменит добавление, родная секция станет заблокированной); перетащите строку на **кнопку фазы** в шапке — это скопирует её в ту фазу. Во время перетаскивания показывается подсказка места вставки (синие линии над и под строкой), зона сброса подсвечивается; если список длиннее видимой области, у верхнего/нижнего края списка происходит автопрокрутка (чем ближе к краю, тем быстрее), так что дотянуть можно и когда пул в свёрнутой области, а целевая строка вне видимой области.
- **Каждая фаза отдельно**: блокировка в фазе ввода пишется в `sectionsBootstrap`, в фазе управляемого сжатия — в `sectionsCompaction`, в постоянной фазе — в `sections`; три списка не наследуются и не влияют друг на друга, пространства сортировки тоже не пересекаются, поэтому «в фазе ввода оставить только 5 секций, а в постоянной фазе включить все» можно выразить отдельно — блокировка / восстановление секции в одной фазе никогда не меняет её состояние в других. Если **перетащить** секцию из пула «Все секции системы» в текущую фазу, она станет независимой копией для этой фазы (в запись добавления этой фазы пишется исходный текст) — добавить секцию в фазу можно только перетаскиванием, у строк в пуле кнопок больше нет, и интерфейс поэтому стал вдвое чище. (Если включить «Синхронизировать фазы», все три фазы делят один список — см. ниже.)
- **Принудительное переопределение (`forceSections`, по умолчанию включено)**: обёртка точки входа сборки хоста включается только тогда, когда у текущего пресета / текущей фазы есть реальная политика секций (блокировка / замена / добавление / сортировка), и тогда итоговые sections пересобираются по результату плагина — при этом обходятся и собственная обрезка секций пресет-плагина по фазам (например, у liangshen в фазе ввода 20 → 1), и полный захват `complete: true` у persona; без кастомизации секций всё остаётся как у хоста (включая complete persona у minimal). Со значением `false` — откат к фильтрации внутри каскада сборки (тогда полный захват секций снова подавляет кастомизацию на уровне секций).
- **Секции промпта инструментов (`tool:*`)**: первая часть инструмента — секция промпта инструмента, зарегистрированная в `systemPrompt`; она появляется в списке промптов как обычная секция, и её можно как обычно блокировать / заменять / сортировать. `description` на странице инструментов — вторая часть (только чтение), JSON Schema параметров — третья (не редактируется). Одна секция `tool:*` может обслуживать несколько инструментов (например, `tool:jobs` соответствует `job_kill/job_list/job_output`), и страница инструментов покажет эту связь.
- **Сворачивание PTC не действует на домен промптов (2.2.0 / ADR-0006)**: когда пресет PTC / Code Mode сворачивает объявления инструментов в один `run_code`, панель явно помечает сворачивание как относящееся к инструментам (`masked-ptc` + баннер), но **список секций, предпросмотр секций и перечисление/редактирование секций `tool:*` работают как обычно** — сворачивание действует только на видимые модели объявления инструментов, секции промпта от него не исчезают, и чтобы увидеть секции, PTC отключать не нужно.
- **Переключатель китайских промптов (панель инструментов в шапке, рядом с кнопкой обновления)**: включён — все секции, чьё имя совпало со встроенным переводом (`lib/zh/`, 25 записей), разом перекрываются китайским текстом; выключен — у этих секций стирается текст замены и возвращается английский оригинал. Оба направления пишутся в черновик редактирования и идут тем же путём сохранения, что и ручное редактирование; состояние переключателя берётся из конфига, новых полей не появляется. Пользовательские секции и секции с несовпавшими именами не затрагиваются, число секций и добавлений не растёт и не падает. Переменные промпта `{{...}}` (например, `{{model}}` / `{{cwd}}` у persona), машинные пути и блоки кода сохраняются дословно; у `tools:sdk` заменяется только вводная проза, а блок TS-кода берётся из оригинала. **`tools:sdk` и `context:file-reference` — переводы через функцию**: переводить или нет решает оригинал этой строки (оригинал пуст = гард этой секции уже стёр её, значит замену пропускаем и никогда не воскрешаем переводом то, что гард убрал); когда переключатель включён и секцию перетаскивают из пула «Все секции системы» в какую-то фазу, тоже предпочитается перевод — добавил и сразу по-китайски, перехват в один шаг.
- **Синхронизация фаз (переключатель «Синхронизировать фазы» в шапке, по умолчанию выключена)**: в момент включения две другие фазы перезаписываются **объединённым набором строк постоянной фазы** (пишется в черновик редактирования, вступает в силу по кнопке «Сохранить»), после чего все три фазы делят один список секций и один текст — добавление / удаление / сортировка / галочки / правка текста пишутся сразу во все три фазы, и щёлкать по каждой фазе отдельно больше не нужно. Каркас порядка берётся из постоянной фазы, секции, существующие только в двух других фазах, дописываются в конец и добавляются в постоянную фазу (одноимённые секции ведут себя так, как в фазе, где они родные); три списка блокировок тоже сводятся к одному. Динамические секции (текст которых генерируется только в рантайме и оригинала не достать) нельзя создать из ниоткуда в другой фазе — список даст пояснение. Блокировка / показ и возврат в двух колонках инструментов тоже действуют на все три фазы сразу (только для одноимённого элемента).

### Каталог инструментов

- **Галочка = инструмент виден модели в этой фазе** (`exclude`): снимаете галочку — инструмент скрывается в **этой фазе**, ставите обратно — восстанавливается; скрытая строка остаётся на месте полупрозрачной. Режима белого списка нет — он обнулил бы `exclude` целиком: одна галочка могла бы тихо выключить все остальные инструменты фазы, а выразительности он не даёт больше, чем инверсия.
- **Список «вернуть» (`add`)**: инструменты, обрезанные в этой фазе, но **ещё существующие в реестре**, можно добавить в фазу из пула «Все инструменты системы» — при сборке после фильтрации schema запрашивается из реестра и добавляется (приоритет у `exclude`: одно имя в обоих списках = скрыт). Инструменты, которых в реестре нет вообще (есть только у другого пресета), добавить нельзя — интерфейс прямо это объяснит.
- **Каталог фаз**: у фазы ввода и фазы управляемого сжатия свои списки exclude / add; приоритет в рантайме — **фаза управляемого сжатия > фаза ввода > статика** — если после сжатия перехода не было и каталог фазы управляемого сжатия настроен, используется он; иначе без перехода используется каталог фазы ввода, а в остальных случаях — статическая фильтрация.
- **Перетаскивание**: перетащите инструмент из пула в список = показать его в текущей фазе (вернуть или выпустить из чёрного списка); перетащите строку обратно в пул = убрать из текущей фазы (для возвращённого — отменить возврат, для родного инструмента — скрыть в этой фазе); перетащите на **кнопку фазы** в шапке = скопировать в ту фазу, **вместе со скрытым/включённым состоянием**, исходная фаза не меняется. Возврат в фазу тоже возможен только перетаскиванием.
- **Потолок расширения — реестр**: вернуть в фазу можно только инструмент, который уже есть в реестре; чтобы появился совершенно новый инструмент, надо менять состав пресета, а не здесь.
- **Порядок**: список включённых в левой колонке, пул «Все инструменты системы» и видимый модели каталог в правой колонке упорядочены по **итоговому порядку каталога хоста** (если у пресета задан `toolOrder`, используется он, иначе алфавит) — больше никакого случайного порядка по перечислению реестра или порядку просмотра.
- **Одноимённые инструменты показываются отдельно**: если другой плагин зарегистрировал в скоупе сессии инструмент с тем же именем, что нативный (например, `read` / `edit` у better-edit, `apply_patch` у apply-patch-edit), в списке появятся **две строки с одинаковым именем**: инструмент плагина — в списке включённых (помечен «уровень сессии», **галочку можно переключать** — снятие действительно убирает его из каталога модели, это реализовано фильтрацией `assembly.tools` после сборки, потому что `restrict` не достаёт до инструментов, зарегистрированных внутри скоупа), а нативный — в read-only пуле «скрытые» (помечен «перекрыт одноимённым», **включить обратно нельзя**).
- **Обёртка исполнителя (`run_code` в PTC)**: появляется в списке включённых как закреплённая строка «обёртка исполнителя», чекбокс отключён (это не обычный инструмент, который можно включать/выключать отдельно).
- **Основной список = фактическое состояние запроса (2.2.0 / ADR-0006)**: в редактируемый список слева попадают только строки с `state ∈ {controllable, locked-agent, locked-executor}` — то, что реально действует в настоящем запросе и что этот плагин может изменить. Определение больше не сводится к сборке в скоупе пресета плагина: оно послойно (global / preset / agent) сравнивает определения с тем же представлением скоупа агента, что у хоста, а бейдж `layer` на строке говорит, на каком слое она зарегистрирована. Элементы, скрытые самим плагином (фаза `exclude`), остаются на месте (полупрозрачные + бейдж «скрыт этим плагином», галочку можно вернуть).
- **Read-only пул делится на две группы (2.2.0)**: пул только для чтения в свёрнутой области больше не свален в кучу, а разделён на **«Можно вернуть (скрыт плагином)»** и **«Вернуть нельзя (решено извне)»** — в первой лежит `masked-own` (скрытие, устроенное самим плагином; в пуле можно сразу вернуть галочкой), во второй — `masked-plugin` (**внешне невидимо**: ограничено `restrict` другого плагина, реестром MCP и т. п.), `masked-shadow` (перекрытие одноимённым, с `shadowedBy` на строку, которая его перекрыла), `masked-ptc` (сворачивание PTC, доступно внутри программной привязки). Группа «Вернуть нельзя» не получает чекбоксов и не пишет списки фаз (запись туда никогда не сработает).
- **Баннер «сессия не привязана» (2.2.0)**: когда у цели редактирования нет активной сессии того же пресета, скоуп agent не получить, и панель сверху показывает баннер «Нет привязанной сессии: активной сессии с этим пресетом нет, внешняя видимость неизвестна», а основной список откатывается к виду скоупа пресета — в этом случае «внешне невидимо» — не вывод, а просто неизвестность.
- **Баннер сворачивания PTC (2.2.0)**: когда пресет сворачивает объявления инструментов в один `run_code`, сверху появляется баннер «Режим PTC: модель получает только `run_code`, остальные инструменты доступны внутри привязки программы…»; свёрнутые строки уходят в группу «Вернуть нельзя (решено извне)». Сворачивание влияет только на объявления инструментов, на секции промпта — нет.
- **Три части инструмента разделены**: секция промпта (`tool:*`, редактируется на вкладке «Промпты»), описание инструмента (на вкладке «Инструменты» только для чтения), JSON Schema параметров (не редактируется); вкладка «Инструменты» отвечает только за видимость инструментов и не подмешивает description / Schema в редактирование промптов.
- Влияет только на каталог, обращённый к модели; сами инструменты и маршрутизация работают как обычно.

### Предпросмотр с точки зрения модели

У предпросмотра два вида:

- **Предпросмотр целевого пресета**: в режиме «Промпты» — итоговый системный промпт, в режиме «Инструменты» — видимый модели каталог; переключается вместе с табами фаз в шапке. С 2.1.0 список промптов и предпросмотр одновременно берутся из реальной сборки «этот пресет + активный агент того же пресета» (ADR-0005) — секции, динамически зарегистрированные плагином в скоупе agent, тоже появляются в списке и правой колонке. **С 2.2.0 каталог инструментов тоже переведён на тот же источник** (ADR-0006): основной список и read-only пул определяются по представлению скоупа агента хоста, а не по схеме «чистая сборка пресета + добор из реестра»; без активной сессии — откат к виду пресета и баннер «Нет привязанной сессии: активной сессии с этим пресетом нет, внешняя видимость неизвестна».
- **Текущая сессия (только чтение)**: маршрут `/session` прогоняет реальную сборку в скоупе агента последней активной корневой сессии и показывает, что модель видит прямо сейчас: промпт, рантайм-контекст и каталог инструментов. С 2.1.0 он и live-вид предпросмотра пресета — **две параллельные точки входа реальной сборки**: предпросмотр пресета вливает только секции активного агента **того же пресета**, read-only вид показывает последнюю корневую сессию; оба перечисляют секции, динамически зарегистрированные при agent/created, и скрытие через `tools.restrict` в скоупе agent.

Вид инструментов даёт сравнение «видит модель / полный каталог» — пресеты вроде PTC и Code Mode пакуют весь каталог в один `run_code`, и по одному реестру ошибиться легко. **С 2.2.0 и список включённых, и read-only пул определяются по «фактическому состоянию запроса»** ([ADR-0006](../adr/0006-effective-view-source.md)): `controllable` / `locked-agent` (на уровне сессии) / `locked-executor` (обёртка исполнителя) остаются в основном списке; `masked-own` уходит в группу «Можно вернуть (скрыт плагином)»; `masked-plugin` / `masked-shadow` / `masked-ptc` — в группу «Вернуть нельзя (решено извне)» (без чекбоксов). Без активной сессии `truth.linked === false` и выводится баннер «Нет привязанной сессии: активной сессии с этим пресетом нет, внешняя видимость неизвестна»; при сворачивании PTC — баннер сворачивания. Одноимённые инструменты окажутся в двух местах: в основном списке (тот, что даёт плагин) и в группе «Вернуть нельзя (решено извне)» (нативный, который перекрыли).

### Переменные промпта

Хост регистрирует только три переменные — `provider` / `model` / `cwd`; ссылка в тексте секции на любое другое `{{name}}` просто завалит всю сборку. Плагин через официальные точки расширения добавляет два вида переменных:

- **Встроенные системные факты**: `date` / `time` / `datetime` / `weekday` / `hostname` / `platform` / `arch` / `username` / `home` / `shell` / `locale` / `node_version` — вычисляются заново при каждой сборке.
- **Полное окружение**: каждый ключ `process.env` маппится в `env_<нижний регистр, недопустимые символы сводятся в _>`, например `PATH` → `{{env_path}}`, `USER.NAME` → `{{env_user_name}}`.

**Чёрный список (`envBlocklist`)**: в env часто лежат секреты, а попав в промпт, они уедут модели вместе с запросом — поэтому ключи, попавшие в чёрный список, не регистрируются. Предзаполненные записи покрывают типичные ключи учётных данных (включая `SECRET` / `TOKEN` / `PASSWORD` / `API_KEY` / `*_DSN` и т. п.), записи поддерживают `*` и нечувствительны к регистру; карточка чёрного списка переменных окружения в панели позволяет добавлять и удалять записи в любой момент, а свёрнутый список в карточке показывает, какие переменные реально зарегистрированы сейчас. Изменения чёрного списка действуют со следующей сборки (правка в панели или прямое редактирование `config.yaml` — без разницы).

**Экспорт / импорт едет вместе**: при экспорте пресета текущий чёрный список пишется в файл вместе с ним; импорт объединяет по принципу объединения (только добавляет, ничего не удаляет), как и семантика библиотеки снапшотов.

Цена строгого рендеринга: если в секции сослаться на незарегистрированное имя (например, на ключ, отсечённый чёрным списком), **вся сборка упадёт**, а не оставит пустое место — не используйте имена, которых нет в списке панели.

### Снапшоты конфига и пресеты агента

- **Сохранить текущую конфигурацию**: полная кастомизация текущего скоупа (включая списки блокировок по фазам, сортировку по фазам, каталоги инструментов по фазам) сохраняется как переиспользуемый снапшот конфига.
- **Применить**: одноимённые секции перекрываются, текущие секции вне списка снапшота по умолчанию блокируются; секции снапшота, которым в текущей системе нет соответствия, по умолчанию пропускаются (при импорте из другой системы секции из ниоткуда не создаются), а поля фаз, которых в снапшоте нет, оставляют ваши текущие значения — их не затирают. Одновременно используется только один снапшот.
- **Экспорт / импорт**: снапшот конфига ходит туда-обратно в JSON (в Tauri-десктопе — через нативный диалог, в Web — через скачивание / выбор файла), одноимённые пресеты пропускаются. Порядок хранится в относительном виде (каждая секция помнит, за кем она идёт), поэтому снапшот переносим между разными наборами секций.
- **Сохранить как пресет агента**: каталог пресета текущей цели редактирования целиком **копируется** (файлы состава, сопутствующие скрипты, каталог скиллов — всё уезжает вместе) в корень пользовательских пресетов, после чего в его оверрайды записывается текущая кастомизация. Новый пресет сразу появляется в табах пресетов в шапке — это настоящий переключаемый пресет агента, а не просто копия конфигурации.

### Пул реестра, общий для пресетов

«Все секции системы / Все инструменты системы» не переключаются вместе с целью редактирования: это **объединение, общее для всех пресетов, которое только растёт** (при одинаковом имени побеждает увиденное позже, новые имена дописываются), хранится оно в производном кэше `catalog.yaml` и пересоздаётся само, если его удалить.

Содержимое пула приходит из трёх мест:

- **Реестр текущего скоупа** (того пресета, который вы редактируете);
- **Сессионные секции / инструменты активного агента того же пресета**: когда цель редактирования — это пресет, к которому относится активный агент того же пресета, список и предпросмотр при запросе сливаются с реальной сборкой этого агента (любые имена секций вроде `tool:subagent`, `context:file-reference`, `tool:undo_last_edit`), дедуплицируются по `{name, source}`, одинаковые имена из разных источников идут отдельными строками и помечаются «уровень сессии»; при переключении на другой пресет остаётся чистый список пресета, чтобы не примешивать чужое (ADR-0005);
- **Просмотренные другие пресеты**: секции / инструменты, зарегистрированные только в каком-то пресете (например, `tools:ptc-only`, `raw-html-v2:vcp`), постепенно вливаются по мере переключения цели редактирования — эта часть растёт по необходимости, и это осознанный выбор плагина (монтировать дерево каждого пресета по очереди — это до десятка секунд, не стоит гонять это при каждом открытии панели).

Та сборка реальной сессии тоже вливает увиденные секции / инструменты в реестр — как фолбэк, когда живого агента нет. `catalog/rescan` тоже читает вид активного агента того же пресета, чтобы повторное сканирование не снесло записи, зарегистрированные только в скоупе agent. Секции в пуле упорядочены по `order` хоста (как их получает модель); в пуле инструментов только пресетные инструменты, которые можно переключать по фазам, — неконтролируемые смотрите в read-only «Полный каталог / скрытые» на вкладке инструментов.

## Инструкции по использованию

Нажмите **Возможности** на боковой панели и выберите сверху вкладку **Промпты**. Первая строка — чипы пресетов агента (с 0.9.0 «Все агенты» убраны — промпты правятся только по конкретному пресету); после выбора пресета изменения действуют только на него, а поля, которые в пресете не кастомизированы, = официальные значения по умолчанию; оранжевая цифра на чипе говорит, сколько пунктов в нём уже поправили отдельно. Вторая строка — шапка кастомизации: переключатель режимов (Промпты / Инструменты / Пресеты), табы фаз (Фаза ввода / Постоянная фаза / Фаза управляемого сжатия — список слева и предпросмотр справа переключают одну и ту же фазу), синхронизация фаз и переключатель китайских промптов, Сохранить / Обновить / Закрыть.

### Режим «Промпты»

Слева перечислены секции текущей фазы:

- **Чекбокс**: попадает ли секция в модель в этой фазе (бейджи `Не заблокировано` / `Заблокировано`); отключённая строка остаётся на месте полупрозрачной, галочку можно вернуть в любой момент
- **Правка**: замена текста секции по фазам, у заменённой строки есть бейдж `Заменено` и кнопка «Вернуть»
- **↑/↓**: меняют порядок внутри этой фазы; `#N` — текущий виртуальный индекс строки
- Бейджи `Системный` / `Вручную` показывают источник секции; удалять можно только секции `Вручную`
- **«Добавить секцию»**: раскрывает форму — по имени + тексту создаётся новая секция (фаза фиксируется текущим табом)
- **Фильтр внизу**: Все / Включены / Отключены, считает только текущую фазу

Read-only пул «Все секции системы» спрятан в свёрнутой области в конце списка: **перетащите строку в список выше** — она добавится в текущую фазу; **перетащите на кнопку фазы в шапке** — она добавится в ту фазу (кнопок на самих строках больше нет). Правая колонка в реальном времени показывает итоговый системный промпт текущей фазы после сборки — эффект черновика виден сразу, а панель помечает «В предпросмотре есть несохранённый черновик».

Если включить в шапке **синхронизацию фаз**, все три фазы делят один список секций и один текст (каркас — постоянная фаза, секции, существующие только в двух других фазах, дописываются в конец и добавляются в постоянную фазу): на каком бы табе фазы вы ни были, список один и тот же, а добавление / удаление / сортировка / галочки / правка текста пишутся во все три фазы сразу — подходит для случая «во всех трёх фазах нужен один и тот же промпт»; без синхронизации каждая фаза сама по себе — подходит для «в фазе ввода оставить несколько секций, а после перехода включить всё».

### Режим «Инструменты»

Слева перечислен каталог, попадающий в фильтр этой фазы, ∪ добавленные вами инструменты: галочка = инструмент виден модели в этой фазе, снятие = скрыт в этой фазе. Пул «Все инструменты системы» спрятан в свёрнутой области: **перетащите строку в список** — она появится в текущей фазе, **перетащите на кнопку фазы** — скопируется в ту фазу (вместе со скрытым состоянием), **перетащите обратно в пул** — уберётся из текущей фазы. Чтобы увидеть, сколько инструментов модель реально получает, смотрите сравнение «видит модель / всего в реестре» в предпросмотре справа.

### Режим «Пресеты»

Слева — **Библиотека снапшотов конфига** (сохранить текущую конфигурацию / импорт / применить / экспорт / удалить; у используемого снапшота пометка «используется»); справа — **сохранить как пресет агента** (целый форк каталога пресета текущей цели редактирования с записью текущей кастомизации) и **глобальные настройки**: переключатель «Принудительное переопределение», чёрный список переменных окружения (добавление и удаление записей, просмотр реально зарегистрированных переменных), справка по переменным промпта, кнопка «Сбросить в исходное состояние» (очищает все кастомизации и выключает `forceSections` — эквивалент удаления плагина, перезапуск не нужен, клик требует второго подтверждения).

### Цель редактирования и сохранение

Таб пресета решает, куда попадут изменения. Режимы промптов и инструментов делят один несохранённый черновик, и кнопка **Сохранить** записывает всё за один раз; переход в режим «Пресеты» или смена цели редактирования отбрасывает черновик (при грязном черновике сначала спросят подтверждение). То есть: испорченное не попадёт в файл, пока вы не нажмёте «Сохранить».

## Где лежит конфигурация

- `~/.dsh/prompt-customizer/config.yaml` — единственный авторитетный конфиг. При первом запуске, если файла нет, а в старом `settings.yaml` есть соответствующие разделы, выполняется разовая автоматическая миграция (основной документ остаётся как есть, откат возможен). Ручные правки действуют сразу, перезапуск не нужен.
- `~/.dsh/prompt-customizer/catalog.yaml` — накопительный реестр секций / инструментов между пресетами, чисто производный кэш: удалите — и он пересоберётся по мере просмотра.
- Сторона скиллов: `.bundles.json` в корнях скиллов (реестр бандлов, хранит и каноническое имя, и имя каталога) и реестр переключателей скиллов (глобальный уровень + уровни пресетов).
- Сторона MCP: глобальные Server — в `$DSH_HOME/mcps/<serverName>/mcp.json` (стандартный `.mcp.json`, намерение «включён/выключен» — в соседнем `.dsh-prompt-customizer.json`, после старта возвращаются в память); строка Server, которую даёт пресет, пишется в `config.plugins` строки объявления этого пресета агента и атомарно записывается `configEditor` DSH в `cordis.patch.yml` профиля; Server уровня воркспейса пишется в `.mcp.json` проекта. `mcp/preset-masks` (реестр послойных перекрытий) и `mcp/tool-disable` (реестр включения/выключения инструментов) по-прежнему в SQLite плагина.

## Известные ограничения

Ниже — выводы, проверенные на практике. В соответствующих случаях панель сама показывает жёлтое предупреждение, гадать не нужно:

- **В некоторых пресетах промпт не состоит из секций.** Если секция зарегистрирована с `complete: true` («полный захват (complete)» у dsh-persona), хост **после** каскада сборки восстанавливает все секции в эту одну секцию. Когда у текущей фазы есть реальная политика секций и включён `forceSections` (по умолчанию), плагин обходит этот механизм в точке входа сборки, и кастомизация на уровне секций работает как обычно; без политики секций complete остаётся как есть; если выставлен `false`, блокировка / замена / добавление / сортировка плагина для таких пресетов не действует (фильтрация инструментов не затронута), а панель прямо пишет: «Секция `deployment:persona` объявляет полный захват (complete)…».
- **Причин потерять секции больше одной.** Кроме захвата `complete`, бывает, что пресет своими правилами обрезает секции в конкретной фазе (на практике у одного пресета в фазе ввода 20 секций → 1, а complete-секции в реестре нет). Поэтому панель делает ещё одно сравнение, не зависящее от механизма: сопоставляет имена секций, которые произвёл плагин, с итоговой сборкой по каждому имени и при расхождении пишет «произведено N секций, модель видит M».
- **Синтетическая сессия предпросмотра может деградировать.** Вид фазы приводится в движение синтетической сессией, и отдельные пресет-плагины на такой сессии падают; тогда эта фаза откатывается к сборке без сессии и помечается «деградировала» — то есть на той фазе вы видите результат без родной обрезки секций по фазам.
- **Замена динамически генерируемой секции фиксирует её содержимое.** Такие секции, как `app:web-surface`, генерируются во время сборки в реальном времени (встраивают текущий Web-порт и т. п.). После замены текст замораживается на значении, которое было при редактировании, и больше не следует за рантаймом; если нужно, чтобы он следовал, используйте блокировку.
- **Разбор текста динамических секций делается по мере возможностей.** Читая динамическую секцию, панель пробует вызвать её функцию-генератор (передавая только минимальный контекст), чтобы показать реальное содержимое; секции, которым нужен более сложный контекст и которые падают при первом вызове, показывают `<динамический>`, на остальные функции это не влияет. Кроме того, секции с переменными вроде `{{model}}` / `{{cwd}}` в списке показываются как **неразвёрнутый шаблон**, а заменённый итоговый текст виден только в предпросмотре справа.
- **Экспорт зависит от того, разрешает ли хост скачивание.** Web-фолбэк идёт через скачивание браузером: если webview хоста молча отбрасывает загрузку, панель всё равно скажет «экспорт успешен», а файл никуда не запишется. Импорт (выбор файла) это не затрагивает.
- **Пул — это объединение «узнал, только когда увидел».** Секции / инструменты текущего скоупа и скоупа **активного агента того же пресета** перечисляются сразу; но секции / инструменты, **зарегистрированные только в другом пресете**, попадут в пул лишь когда вы переключитесь на ту цель редактирования (монтировать дерево каждого пресета по очереди слишком медленно, прогрев не делается). У пула нет авторитетных сведений о том, «какому имени какая фаза принадлежит», — при добавлении в фазу запись ложится в текущий таб, а потом её можно перетащить куда угодно.
- **Расширение каталога инструментов ограничено реестром** — см. выше «Потолок расширения — реестр».
- **Определение «текущей сессии»**: панель — синглтон на уровне процесса, клиент не получает id текущей сессии во время рендеринга, поэтому за основу берётся **последняя созданная корневая сессия** (по убыванию `session.header.createdAt`, субагенты с `delegationDepth > 0` не считаются); при переключении между несколькими сессиями панель может продолжать показывать набор скиллов и вид «текущей сессии» той, что создана позже всех. Без сессии — откат к глобальному виду с cwd запуска. Набор записываемых корней по-прежнему пересчитывается только «при монтировании плагина» и «при создании новой сессии (`agent/created`)».
- **Границы видимости инструментов**: фильтрация инструментов по фазам у плагина двухслойная — унаследованные глобальные инструменты идут через `tools.restrict` (только сужение, пересечение), а инструменты, зарегистрированные внутри скоупа (`read` / `edit` / `apply_patch` и т. п. от плагинов), — через **фильтрацию `assembly.tools` после сборки** (удаление по имени из таблицы функций модели), поэтому и те, и другие плагин может скрывать по фазам. Всё, что за границами, больше не притворяется доступным для галочки (2.2.0 / ADR-0006): ① глобальные инструменты, ограниченные `restrict` другого плагина, ② нативные инструменты, перекрытые одноимённым инструментом другого плагина → уходят в read-only пул в группу «Вернуть нельзя (решено извне)» (`masked-plugin` / `masked-shadow`); публичного API атрибуции у хоста нет, поэтому пишется только «внешне невидимо», без указания, какой именно плагин. ③ В PTC / code-mode объявления инструментов свёрнуты в `run_code` → свёрнутые строки помечаются `masked-ptc` и уходят в группу «Вернуть нельзя (решено извне)»; инструменты, вызываемые внутри программы `run_code`, берутся из toolSet, и скрытие плагином `assembly.tools` по имени влияет только на видимую модели таблицу функций, но не на привязки внутри программы.
- **Каталог mcps смонтирован только для чтения**: панель не переписывает эти `mcp.json`; чтобы какой-то Server стал постоянной глобальной конфигурацией, по-прежнему нужно «Добавить MCP-сервер» (запись в реестр SQLite плагина, после старта — обратно в память). Имена инструментов Server уровня воркспейса несут 8-символьный суффикс хэша пути (например, `mcp__codegraph-e5f6a7b8__*`) — такова цена изоляции одноимённых инструментов.

## Разработка

```bash
npm install
npm run check   # typecheck + build + все юнит-тесты
```

Обе стороны собираются один раз через [esbuild](https://esbuild.github.io/) (`node build.mjs`):

- `lib/index.js` — хостовая половина, ESM, самодостаточная, из зависимостей остаются только встроенные `node:*`; `@deepseek-ai/*` всегда идёт через `vendor/` (встроенные листовые модули) или инлайнится во время сборки, а `assertHostExternals()` в конце сборки валит нарушившие правило bare-импорты;
- `client/client.js` — браузерная половина, factory-бандл `__ModuleLoader__`; `react*` и `@deepseek-ai/*` идут через таблицу модулей хоста, всё остальное инлайнится.

Изменения в браузерной половине нельзя проверять одними юнит-тестами (исторически так и просочился «клик по вкладке MCP и падение»: юнит-тесты все зелёные, а на реальном рендере рвётся). Две целевые проверки:

```bash
# 1) статический предохранитель: имена, импортированные из ui-primitives хоста, должны реально существовать (защита от undefined-компонентов)
node --test test/client-primitives.test.mjs

# 2) настоящий браузер: поднять dsh web и руками прокликать панель в настоящем Chrome со скриншотами
dsh web --port 3099 --no-open          # взять из вывода URL с токеном
node scripts/verify-panel-browser.mjs --url "<URL с токеном>" \
  --expect-skills <имена скиллов,...> --expect-mcp <serverName,...> --out ./verify-shots
```

`--headless` переключает в headless; скрипт использует только встроенные возможности Node (`fetch` + `WebSocket` для управления CDP) и не тянет сторонних зависимостей.

Фазовые и тестируемые чистые части логики собраны в `vendor/prompt-customizer/` (политики промптов / реестр списка / проекция фаз) и `vendor/skill-manager/`: одни и те же чистые функции и упаковываются в обе половины, и напрямую покрываются `node --test` — тесты и есть боевой код. `npm run check` = сборка + полный прогон юнит-тестов + smoke двух половин.
